# 第二轮优化性能报告

## 环境说明

本报告记录第二轮优化后在本地模拟环境中的压测结果。测试目标是对比字典化开启和关闭时，30 万行数据、100 个请求、4 个输出字段下的加密与写盘能力。

请求字段固定为：

```json
["phone", "user_code", "user_id", "name"]
```

说明：

- `phone`、`name` 为掩码字段，加载期预计算。
- `user_code`、`user_id` 为 SM4 字段，也是本轮默认字典化字段。
- 每个请求使用相同测试密钥 `2123433411630000`。
- 输出文件数为 100。
- 每个输出文件 30 万行。

## 验证方式

由于当前 shell 环境没有可用 `mvn` 命令，验证分为两部分：

1. 使用本地 Maven 仓库依赖手工执行 Java 11 编译检查。
2. 使用临时运行产物和直接调用 `EncryptService.generateBlocking` 的方式进行核心压测。

HTTP 方式曾用于 `perf_data_300000.csv` 对照压测；`perf_data_low_cache_300000.csv` 因后台服务启动审批超时，改用核心路径压测。核心路径覆盖 CSV 加载、SM4 加密、字典化、CSV 写盘，但不包含 HTTP 提交开销。

## 高重复数据压测

数据集：

```text
perf_data_300000.csv
```

压测方式：

- 启动临时 Spring Boot 运行产物。
- 调用 `/health`。
- 并发提交 100 个 `/encrypt` 请求。
- 等待 100 个 CSV 文件生成且大小稳定。

结果：

| 方案 | HTTP 提交耗时 | 全部完成耗时 | 输出文件 | 总输出 | 输出吞吐 |
|---|---:|---:|---:|---:|---:|
| 字典化开启 | 158 ms | **6.22 s** | 100 | 2317.43 MB | **372.76 MB/s** |
| 字典化关闭 | 228 ms | 10.31 s | 100 | 2317.43 MB | 224.80 MB/s |

收益：

```text
总耗时下降约 39.7%
输出吞吐提升约 65.8%
```

## 低缓存命中数据压测

数据集：

```text
perf_data_low_cache_300000.csv
```

该数据集在加载期统计到的字典唯一值如下：

| 字段 | 唯一值数量 |
|---|---:|
| user_id | 90000 |
| user_code | 294463 |
| secret_code | 100000 |

压测方式：

- 直接调用 `EncryptService.generateBlocking`。
- 使用 3 个工作线程并发生成 100 个请求输出。
- 覆盖 CSV 加载、SM4 加密、字典化和写盘路径。
- 不包含 HTTP 提交耗时。

结果：

| 方案 | 全部完成耗时 | 输出文件 | 总输出 | 输出吞吐 |
|---|---:|---:|---:|---:|
| 字典化开启 | **7.59 s** | 100 | 2317.43 MB | **305.53 MB/s** |
| 字典化关闭 | 11.79 s | 100 | 2317.43 MB | 196.51 MB/s |

收益：

```text
总耗时下降约 35.6%
输出吞吐提升约 55.5%
```

## 结论

第二轮优化在两个 30 万行数据集上均有明显收益。

核心原因是：

1. `user_id`、`user_code` 等字段的重复关系在加载期被整理为字典。
2. 请求阶段对字典字段只加密唯一值，而不是逐行加密。
3. 写 CSV 时使用请求级快速缓冲，减少细碎写调用。

当前实现即使在 `perf_data_low_cache_300000.csv` 中 `user_code` 基本接近全唯一，仍然因为 `user_id` 有明显重复、写盘路径更轻，整体表现优于关闭字典化的路径。

## 后续建议

下一步可以把字典化从固定字段推进为采样自适应：

- 加载前 N 行估算字段重复率。
- 重复率高于阈值时启用字典。
- 接近全唯一的字段继续走普通列式加密路径。

这样可以避免 `user_code` 这类接近全唯一字段在低缓存命中数据中建立较大字典，进一步降低加载内存和请求前置加密成本。
