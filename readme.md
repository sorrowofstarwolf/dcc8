在数据动态脱敏业务场景中，数据在内存中的脱敏处理时间直接影响最终数据脱敏的效率，从而影响用户通过动态脱敏应用查询数据库的感知时间。为减少用户在查询时的等待时间，优化脱敏执行时间显得尤为重    要，实际业务场景中，小服务器的高并发数据处理是常见痛点。常见的脱敏算法中，SM4对称加密作为国密标准，因加密强度高、耗时较长，对服务器压力和编程优化能力要求更高，也成为了影响脱敏效率的瓶颈(见时间T4)。

本次比赛模拟真实高安全业务场景，引入动态SM4密钥机制，要求选手在小服务器资源约束下，完成多字段SM4动态加密与脱敏处理，同时应对100个并发查询请求，兼顾内存稳定性、结果准确性与响应速度，优化方案可直接落地实际生产，提升数据脱敏应用的脱敏效率，减少用户查询等待时间，本次比赛核心聚焦“小资源+高并发+动态SM4加密处理”。

# 二、**课题简述**

        本课题要求选手在统一的4C8G服务器环境中，完成指定数据加密，加密算法主要为SM4加密算法，部分字段为掩码脱敏，同时应对100个并发查询请求，每个查询携带独立随机SM4密钥。核心目标：不出现内存崩溃、查询结果100%准确、并发返回速度最快。

## 2\.1 脱敏规则简述

        SM4算法：SM4是中国国家密码管理局发布的分组密码算法，属于国密算法之一，广泛应用于数据加密领域。其分组长度：128位；密钥长度：128位；采用迭代式Feistel网络，共32轮。行内ZA21框架集成，依赖为：ZA33:PCJava:com.cmbchina.channel.api.pkcs10.SM4，核心开源依赖:org.bouncycastle:bcprov-jdk15on，可根据不同的密钥将不同明文加密成不同密文。
    
        掩码脱敏：如果敏感字段小于等于6个字符，则脱敏为“首字+5个#号”；如果敏感字段大于6个字符，则脱敏为“首字+四个#号+尾字”。

形如:zhangsan@qq.com ->(掩码脱敏)  z####m，1823 ->(掩码脱敏) 1#####

## 2\.2 比赛任务要点

* SM4动态加密高效调用与优化：适配每次查询的独立密钥，降低加密耗时，适配小服务器性能
* 内存优化：避免内存泄漏、控制内存占用，防止崩溃，适配服务器低内存约束
* 高并发查询处理：100个并发请求的调度优化，减少响应延迟，兼顾密钥接收与实时计算
* 小资源场景下的计算资源最大化利用：适配低CPU、低内存配置，平衡并发调度与加密计算耗时

比赛输入为1个CSV文件，其中包含30万条结构化数据，11个字段，总数据量约41MB，无空值、无异常值。文件编码格式：UTF-8，CSV中字段如下

| 加密方式 | SM4 | SM4 | SM4 | SM4 | 掩码脱敏 | 掩码脱敏 | 掩码脱敏 | 掩码脱敏 | SM4 | SM4 | SM4 |
| 业务说明 | 用户标识 | 业务流水号 | 用户编码 | 业务密钥 | 身份证号 | 手机号码 | 用户姓名 | 用户邮箱 | 设备唯一标识 | 交易唯一编号 | 用户隐私验证码 |
| 示例 | 10002 | 1219879811312 | ACSE | 12s@\_ks13 | 12331219870918213X | 15669990363 | 阿蕾奇诺 | lyj6169@cmbchina.com | 00:1A:2B:3C:4D:5E | 198726301971241765 | 0E6A23 |
| 格式说明 | 5位数字 | 13位数字 | 4位字母 | 不定长数字、字母、特殊符号，最大长度16位 | 18位数字字母组合 | 11位数字 | 中文 | 中英文特殊字符 | 十六进制数字，特殊字符 | 18位数字 | 6位数字字母 |

### 2\.3.2 加密请求

比赛采用RESTFUL API接口形式向用户发送加密请求，要求用户对11个字段中的部分字段加密处理，请求中包含：

* 一个SM4加密密钥，表示该次调用SM4加密使用密钥，加密密钥格式固定位128位（16字节），示例如：2123433411630000
* 本次查询需要加密的字段名称，以LIST形式给出。LIST含5~7个字段，其中SM4加密字段含3到4个
* 加密请求整体格式如下：

```json
{
  "requestId": "REQ_20260413120000_8765",
  "sm4Key": "2123433411630000",
  "ip":"55.51.53.74",
  "fieldsToEncrypt": [
    "phone",
    "user_code"
  ]
}
```

```
`SM4` 规则：

- 模式：`SM4-CBC`
- IV：固定字符串 `1234567890123456`
- padding：按样例对齐为 `PKCS5/PKCS7`
- 输出：大写十六进制字符串/字节
```

### 2\.3.3 查询并发

比赛会同时发起100个并发调用接口查询，接口响应逻辑为：


启动程序->调用/health接口，判断程序是否启动->发起/encrypt请求加密->回调验证程序接口

验证程序收到回调请求后会立即验证本次请求的文件正确性。

限制！！！！！！！

：

/health启动之前不要做其他任何与加密业务有关操作，包括且不局限于：
1、读取未加密文件
2、申请加密用内存
3、初始化加密服务以及任何与加密相关的操作

## 2\.4 比赛输出数据

### 2\.4.1 加密后数据

加密后密文以CSV文件格式写在硬盘上，编码格式：UTF-8，不含表头，且不要使用""号包裹每个值,注意不要写成UTF8-BOM格式。加密后密文为二进制的，需先转为十六进制字符串后再写入csv文件，样例可参考baseline。

文件字段顺序按照接口中fieldsToEncrypt字段顺序填写。请注意文件输出完毕后需要显式close。

文件输出目录为**/opt/app/dcc/${队伍编号}/output/**，文件名称为请求ID:requestId，如上述示例请求绝对路径为：**/opt/app/dcc/team16/output/REQ_20260413120000_8765.csv**。

请选手在输出文件时保障输出文件行与输入文件行一致，即输出文件的第N行为输入文件第N行的加密，以确保输出文件后续校验。不需要输出文件行号，举例：

输入文件：

| 阿雷奇诺 | 1219879811312 |
| 哥伦比亚 | 1219879811313 |
| 达达利亚 | 1219879811314 |

输出文件：

| 阿##### | 1AB281CDF17892D9 |

| 哥##### | 2BDC197182190981 |
